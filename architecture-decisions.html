Spend compute
where it matters.

The problems, existing designs, and research ideas behind a deeply customized computer-use model.

The goal

Reliable actions across long tasks, with fast responses on easy steps and useful deliberation on hard ones. These are independent design choices to assess before selecting an architecture.

Primary-source research · Proposed adaptations are labeled as ideas.

One action.
Several kinds of cost.

A forward pass evaluates a network. A model call can contain many passes; a task can contain many calls. Each level offers a different place to improve efficiency.

Work that repeats

Mostly unchanged screens, long histories, verbose reasoning, and repeated planning can consume compute without improving the next decision. OSWorld-Human found planning and reflection calls dominated latency in its studied system.

Information that is missing

Hidden app state, tiny controls, forgotten constraints, and delayed UI changes can break a task. More thinking cannot recover information the model never observed. OSWorld 2.0 exposes these long-task failures.

Decision lens: identify whether each failure needs better perception, more reasoning, better memory, or fewer execution mistakes. “Use a bigger model” combines these into one expensive change.

The designs
you can build on.

A VLM combines vision and language. The backbone does the main processing; a head produces a specific output. Computer-use specialization can change either, or both.

DesignWhat it changesDecision it informs
General VLMVision encoder + connector + language backbone. Qwen3-VL includes dense and mixture-of-experts variants.Dense models use all feed-forward weights; MoE selects experts per token. MoE adds capacity without activating every expert, but does not by itself decide how long to think.
Native GUI modelUI-TARS specializes perception, reasoning, and action generation. ShowUI also selects visual tokens.A pretrained VLM already provides much of the foundation. Customization can target screen processing and action outputs.
Adaptive GUI modeliSHIFT combines latent thinking with an optional detailed-perception path.Adaptive computation inside a GUI model already has precedent. Its evidence does not establish reliable performance on arbitrary long desktop workflows.
World-model approachCUWM simulates future screens; Latent2World shares action and transition representations.Prediction can be a separate simulator or part of the decision model. Both directions have prior art.

Outside the network: UFO2 changes agent orchestration and OS integration. vLLM caching changes serving efficiency. A custom model still needs execution software; novel layers may require custom serving support.

What should
“think harder” mean?

Hardness varies within a task. A long workflow can contain easy clicks; one unfamiliar dialog can require careful reasoning. Allocate effort per decision, with a task-level budget.

OptionExisting evidenceMain tradeoff
Variable reasoning lengthFocus switches fast/slow GUI grounding. GPRO separates perception and reasoning paths in VLMs.Easy to explore with a pretrained decoder. Long answers can add latency without correcting the underlying error.
Latent deliberationCoconut feeds hidden states back as inputs. iSHIFT applies latent thinking to GUI actions.Potentially fewer language tokens. Hidden iterations still cost forward passes and are harder to inspect.
Recurrent depthHuginn repeats a shared block to increase computation within a language model.Changes the core network. GUI transfer is an experiment; more iterations need a useful stopping rule.
Selective computationMixture-of-Depths routes selected tokens through layers under a compute budget.Can reduce work within a pass. Token importance and whole-task difficulty are different signals; efficient routing needs compatible kernels.

Decisions: what triggers more compute, which kind is added, and when does it stop? Candidate signals include action disagreement, visual ambiguity, failed checks, and predicted task progress. A confident model can still be wrong; test whether the trigger predicts the benefit of more compute.

Masking is
several different choices.

Decide what gets hidden or skipped. Restricting information, eliminating computation, and ruling out an action are distinct operations.

MechanismWhat it doesWhat can go wrong
Visual token pruningRemove redundant image tokens before or within the backbone. ShowUI is a GUI-specific example.Drops small controls or state cues. Pruning after the vision encoder saves downstream work, not the encoding already done.
Selective perceptionKeep a global view, then inspect relevant detail. iSHIFT adds an optional perception path; FastVLM redesigns the encoder.A bad region choice hides the answer. An extra crop or encoder call must repay its cost.
Attention maskingLimit which tokens can read one another, such as local screen regions or selected history.A dense attention mask can still compute dense matrices. Speed requires actual skipped work or an efficient sparse implementation.
Action maskingExclude actions or targets known to be invalid, such as a disabled control.A wrong mask can remove the only valid action. UI metadata is useful when available; predicted validity is uncertain.
Masked learningHide input regions during learning and predict missing information, as in masked autoencoders.A representation-learning choice. It does not automatically make deployed inference cheaper.

Sources: ShowUI, FastVLM, attention-mask semantics, invalid-action masking, and masked autoencoders. Action-masking evidence here comes from reinforcement-learning environments, not arbitrary desktop apps.

Why “ignore the background” is too simple

Where and How to Prune (2026, v4) finds that both foreground/background balance and spatial coverage matter for GUI navigation. It also distinguishes caching identical historical screenshot embeddings from pruning tokens inside the language model. Reusing an identical image is much easier than safely updating only changed regions of a new image.

Decisions: what information must remain visible, who selects it, and where is computation actually removed? Keep a way to expand the view when a crop, mask, or prediction proves insufficient.

Choose what
prediction is for.

Predicting an action, its consequence, and whether it advances the goal are different tasks. A plausible future can still be the wrong outcome.

Prediction targetPossible useCost or limitation
Next action(s)Produce a short action sequence to reduce model round trips.Later actions may rely on a screen that has not appeared. Stop or replan when assumptions fail.
Future statePredict the UI change caused by a candidate action, in pixels, text, or a compact numerical representation.Pixel generation is expensive; compact predictions can omit important details. Errors accumulate across imagined steps.
Progress or successScore whether an action or imagined state advances the goal.Provides a basis for comparing options, but the score can be wrong. It needs checks against real task outcomes.
Expected observationCompare a prediction with what actually happened to detect a failed action.Visual difference alone is insufficient: a spinner may be harmless, while an unchanged permission state may matter.

Prediction used while learning

A shared prediction head may improve the features used to choose actions. Removing it at deployment avoids its runtime cost, but leaves no explicit online lookahead.

Prediction used while acting

Keep the predictor and evaluate a few candidate futures. This adds computation, plus a need to score outcomes. Usefulness depends on avoided mistakes and the reliability of predictions.

CUWM demonstrates explicit future-screen search. Latent2World’s author-posted preprint is close prior art for shared latent prediction: it discards its transition head but retains selective action rescoring. Neither establishes savings for every proposed integration.

Decisions: predict what, over how many steps, and only when? Specify how a mismatch causes re-observation or replanning. Unlike speculative token decoding, real clicks may have effects that cannot be undone.

Remember the task.
Express the action.

Long-horizon ability also depends on retaining the right facts and controlling the interface precisely. These deserve separate design choices.

ChoiceOptions to compareTradeoff to resolve
Persistent stateFull history; selected observations; learned memory tokens; explicit task facts and retrieved records.Full history costs attention and memory. Compression can erase constraints. KV caching reuses computation; it is not a guarantee of useful task memory.
Action representationGenerated command text; direct heads for action type and coordinates; pointers to detected UI elements; a hybrid with generated typing text.Direct outputs may cut decoding passes. Element pointers depend on candidate detection; coordinates need precision. Shorter output alone does not ensure better actions.
Action horizonOne action per observation; a short action chunk; hierarchical subgoals with frequent checks.Chunks reduce round trips but delay feedback. More frequent checks cost time while improving recovery.
Observation sourceScreenshots alone; screenshots plus accessibility/DOM information, app APIs, or execution events.Pixels work across many interfaces. Structured inputs can reveal useful state but depend on platform coverage and must match the benchmark’s allowed tools.

Recurrent Memory Transformer is a language-model precedent for learned memory across segments. Qwen-UI-Agent (2026) already batches actions and combines GUI/CLI tools. UFO2 illustrates deep OS integration. GUI gains from new memory or action heads remain hypotheses.

Ideas worth keeping open

Task-state slots: preserve goals, completed steps, unresolved questions, and evidence that a change succeeded. Changed-region updates: reuse stable visual state while inspecting changes, with periodic full refreshes. Adaptive action chunks: lengthen sequences only where the next state is predictable. These are design hypotheses, not demonstrated features of a chosen architecture.

The tradeoffs
that should decide it.

Architecture choices interact. Improvement means completing more real tasks within an acceptable time and compute budget.

  • Pruning × predictionA predictor cannot recover an unseen status change reliably. Preserve the evidence needed to verify its forecast.
  • Deliberation × observationSpend longer on reasoning when the evidence is sufficient. Gather evidence when the missing piece is outside the model.
  • Recurrence × deploymentReusing a block saves parameters, but repeated execution still costs time. Irregular paths may reduce batching efficiency.
  • Memory × groundingRemember task facts while refreshing coordinates and transient UI state. A useful memory can still become stale.
  • Specialization × flexibilityDedicated action heads can be efficient. New tools, action types, and continuous dragging make a fixed output space harder to extend.
  • Reuse × architectural freedomNew heads or perception modules can reuse much of a pretrained model. Replacing its recurrent or attention core may require much more adaptation and validation.

Evidence that would make an option worth choosing

Measure screen-encoding time, input-processing time, generation passes, tool waits, and retries separately. Compare task success against total cost per completed task, counting failed attempts. Report median and slow-case latency, easy/hard subsets, and performance on unfamiliar apps.

Keep hardware, tools, and budgets comparable. Check individual changes and their combinations on live task benchmarks such as OSWorld 2.0; a grounding score or fewer theoretical operations cannot establish an end-to-end gain.

Reading notes: where the evidence is strongest
  • GUI-specific adaptivity: iSHIFT and Focus are direct precedents. Grounding and action-matching evaluations have narrower scope than sustained desktop task completion.
  • Deeper core changes: Huginn, Coconut, Mixture-of-Depths, and Recurrent Memory Transformer provide mechanisms from language-model research. Transferring them to GUI tasks is a research question.
  • Perception and efficiency: FastVLM studies visual encoding; ShowUI and Where and How to Prune address GUI tokens. GPRO studies routing between perception and reasoning in VLMs.
  • Prediction and speculation: CUWM and Latent2World address future UI state. Medusa addresses future language tokens; its verification guarantees do not transfer to real-world tool effects.
  • Interpret results carefully: paper-reported improvements are specific to their baselines, tasks, and hardware. This brief makes no novelty claim or performance forecast for a combined model.
